### 2026-09-26 · engagement · d1-brd · electronics-distribution, pricing, quoting
A discount a rep applies from memory is a judgement; the same discount pre-filled by a system is a price policy. When a quote workflow is asked to hold per-reseller discount terms, the requirement is small, but it brings a go-live dependency the request never mentioned: the terms have to be found, written down in one shape, and signed by someone commercial before they are loaded — otherwise the build turns today's habits into policy nobody agreed to. Write the pre-fill, the override-with-reason and the no-terms-on-file path as requirements, and write the signed terms list as a go-live constraint with an owner. Also record the shape you assumed (one number per reseller), because if the terms vary by product, quantity or contract, the requirement grows into a pricing rules table.

### 2026-09-26 · engagement · d2-backlog · backlog, decomposition, ownership
A requirement that gives a unit of work one owner and lets only that owner hand it on reads as contention control, but it also decides what happens when the owner leaves: the work is stuck, and that is the very loss the system was bought to stop. Decomposition surfaces this only when someone writes the unhappy path for the owner's absence, not for two people acting at once. The fix usually adds a role the requirements never named — here an internal admin who can reassign — so it is scope, not detail: write it as its own story, trace it to the ownership requirement, and flag it as an extension for the approver to confirm rather than folding it into an existing story. Worth checking wherever a requirement says 'one owner at a time'.

### 2026-09-26 · engagement · d2-backlog · backlog, time, measurement
When a rep keys in a request that arrived earlier by phone or email, a system-stamped received time records when it was entered, not when it arrived. Every oldest-first queue, turnaround figure and 'untracked by next day' measure built on that time is then quietly wrong for exactly the requests the manual-entry path exists to capture, including the bulk re-entry on go-live day. Ask at decomposition whether 'received' means arrived or entered for every path that is not self-service, before the criteria fix one reading.

### 2026-09-26 · engagement · v1-architecture · architecture, identifiers, backup
When customers hold an identifier on paper, choosing its format is an architecture decision, not a detail. A counter has two costs that are easy to miss: any customer comparing two of their own IDs learns the business's volume, and a restore from backup hands out again numbers already printed on customers' emails. Random codes from an alphabet with no look-alikes remove both. But do the birthday arithmetic before writing down a collision rate: 1.8 million draws from 850 billion codes repeat an existing ID about twice, not once in centuries. The unique constraint and a redraw make that harmless, and the record has to say so correctly, because an EA who checks the arithmetic and finds it wrong stops trusting the rest of the record.

### 2026-09-26 · engagement · v1-architecture · architecture, sql-server, ledger, local-first, verification
When a design runs one database engine locally and another in production, a feature combination the production engine forbids passes every local test and every demo, and fails at the first real deployment. Here an updatable ledger table was also given a full-text index. SQL Server does not allow that, and the SQLite stand-in never complained. It was caught only by reading Microsoft's ledger limitations page while checking a reviewer's claim about tiers. Before committing to a guarantee that rests on an engine feature (ledger, temporal tables, full-text), read that feature's limitations page against every table that uses it, and run contract tests against the real engine from the first story, not from the cloud stage.

### 2026-09-26 · engagement · v2-build · testing-strategy, definition-of-done
A per-criterion check is declared as a command before the code exists, and its working directory is part of the command. Written as though it would run from the engagement folder, every check pointed one level up, exited with npm's 'no package.json' code and failed for a reason unrelated to the build; the run recorded 0 of 19 at a commit where every underlying test passed. Run one declared command through the recorder before the first real run, not a hand-run from your own shell, and when the declaration has to be corrected, say so in the declaration so the failed run on the record reads as what it was.

### 2026-09-26 · engagement · v2-build · testing-strategy, mutation
Three random line mutations per check across a build that also adds screens, seed data and scripts mostly land where a criterion does not look, so most per-criterion checks 'survive' and the summary reads as weak checks. Given eight mutations the same check noticed a flipped comparison in the route guard. The survival count measures where the mutations fell as much as the checks; the sharper evidence was building the plausible-wrong implementation for three criteria (duplicates refused only at different prices, roles cached at first read, blank part-number rows skipped) — each was caught by exactly the tests owning its criterion and nothing else. Report both, and do not let either stand in for the other.

### 2026-09-26 · engagement · v3-qa · testing-strategy, data-migration, state-transition
Three sound rules can combine into a trap no single story shows. A one-off import refused onto a non-empty store (to protect maintained prices), an add-product action open from day one, and records nobody can delete meant that one product added before the go-live import blocked the import permanently, with no recovery inside the system. Each story passed on its own; only a cross-story case run in the wrong order (add, then load) showed it. Wherever a one-time operation guards itself with 'only when empty', test the path where something else fills the store first, and ask what removes it.
— bow-electronics-reseller-portal / note / e52baea488a1
### 2026-09-26 · engagement · v3-qa · testing-strategy, non-functional, performance
A latency figure taken on a shared workstation measures the workstation. The same build gave a p95 of 256 ms and 2,288 ms for 50 concurrent searches over 250,000 products in consecutive runs, while unrelated processes held the load average at 20-25 on a 10-core machine; one search at a time cost under 40 ms throughout. Record the host load beside every timing, run it at least three times, and report a spread that wide as needs-clean-retest rather than as a pass or a fail.
— bow-electronics-reseller-portal / note / 20fe713b8de3
