# Briefing — v4-handover

Compiled by rule from the memory stores — nothing here was written by a model. Read it before the inputs; act on what applies; note what you learn with `raise memory note`.

## From the engagement

- **2026-09-26 · v3-qa** — A latency figure taken on a shared workstation measures the workstation. The same build gave a p95 of 256 ms and 2,288 ms for 50 concurrent searches over 250,000 products in consecutive runs, while unrelated processes held the load average at 20-25 on a 10-core machine; one search at a time cost under 40 ms throughout. Record the host load beside every timing, run it at least three times, and report a spread that wide as needs-clean-retest rather than as a pass or a fail. _(bow-electronics-reseller-portal, note)_
- **2026-09-26 · d1-brd** — A discount a rep applies from memory is a judgement; the same discount pre-filled by a system is a price policy. When a quote workflow is asked to hold per-reseller discount terms, the requirement is small, but it brings a go-live dependency the request never mentioned: the terms have to be found, written down in one shape, and signed by someone commercial before they are loaded — otherwise the build turns today's habits into policy nobody agreed to. Write the pre-fill, the override-with-reason and the no-terms-on-file path as requirements, and write the signed terms list as a go-live constraint with an owner. Also record the shape you assumed (one number per reseller), because if the terms vary by product, quantity or contract, the requirement grows into a pricing rules table. _(bow-electronics-reseller-portal, note)_
- **2026-09-26 · v2-build** — A per-criterion check is declared as a command before the code exists, and its working directory is part of the command. Written as though it would run from the engagement folder, every check pointed one level up, exited with npm's 'no package.json' code and failed for a reason unrelated to the build; the run recorded 0 of 19 at a commit where every underlying test passed. Run one declared command through the recorder before the first real run, not a hand-run from your own shell, and when the declaration has to be corrected, say so in the declaration so the failed run on the record reads as what it was. _(bow-electronics-reseller-portal, note)_
- **2026-09-26 · v2-build** — Three random line mutations per check across a build that also adds screens, seed data and scripts mostly land where a criterion does not look, so most per-criterion checks 'survive' and the summary reads as weak checks. Given eight mutations the same check noticed a flipped comparison in the route guard. The survival count measures where the mutations fell as much as the checks; the sharper evidence was building the plausible-wrong implementation for three criteria (duplicates refused only at different prices, roles cached at first read, blank part-number rows skipped) — each was caught by exactly the tests owning its criterion and nothing else. Report both, and do not let either stand in for the other. _(bow-electronics-reseller-portal, note)_
- **2026-09-26 · v3-qa** — Three sound rules can combine into a trap no single story shows. A one-off import refused onto a non-empty store (to protect maintained prices), an add-product action open from day one, and records nobody can delete meant that one product added before the go-live import blocked the import permanently, with no recovery inside the system. Each story passed on its own; only a cross-story case run in the wrong order (add, then load) showed it. Wherever a one-time operation guards itself with 'only when empty', test the path where something else fills the store first, and ask what removes it. _(bow-electronics-reseller-portal, note)_

## From the practice

- **2026-09-23 · v4-handover** — A component the architecture names as a build deliverable, traced to requirements and explicitly marked not-deferred, can be absent at handover with every gate still green — because no gate reads the component table back against the repository. Here a restore runbook carrying the one step that stops a snapshot restore re-issuing identifiers customers hold on paper was named in the components table, traced to two requirements, assigned to Build, and never written; no story in the approved backlog carried it, no QA round looked for it, and the risk it mitigates was recorded as mitigated throughout. The check that finds it is cheap and belongs at handover: take the architecture's component table, and for each row owned by Build that is not code, search the record, the backlog and the source for the thing itself. Non-code deliverables — runbooks, procedures, configuration a human performs — are the ones that slip, because every other artifact discusses them without producing them. _(practice, ddef37f0a254)_
- **2026-09-23 · v3-qa** — A rate limiter is the same check-then-act shape as an idempotency token, and the natural way to test one hides the bug completely. A lookup throttle that must refuse the eleventh failure in a window did exactly that sequentially — ten answered, the eleventh refused, at every boundary including the window edge and the lockout lift — and admitted 100 of 100 when the same visitor issued the lookups concurrently. The count was not lost; the lockout armed immediately afterwards. What failed is that every request in the burst read the pre-increment count before any of them wrote. Sequential iteration is how a throttle test gets written, so the whole suite can be green over a control that any caller opening two connections can walk through. Fire the burst concurrently at several widths and compare answered-versus-refused against what the criterion allows; and where a threat was accepted on the record because a control mitigates it, test the control for bypass rather than for presence — the accepted risk is only as accepted as the mitigation is real. _(practice, 0093ab0fa425)_
- **2026-09-23 · v2-build** — An idempotency token that is read before the write and marked after it is check-then-act, and a double-click defeats it: two requests both find the token unspent, both write, and one intent produces two records. The await between the check and the mark is the whole bug, and it is invisible to a test that replays the request sequentially — which is the natural way to write that test. Claim the write before the first await and have the second request wait on it. Worth checking wherever a one-time token, a nonce or a dedupe key guards a write. _(practice, 2fc52b882485)_
- **2026-09-23 · v3-qa** — A sequence allocator whose configured seed is validated with Number.isInteger accepts values at or above 2^53, where incrementing is a no-op: two records then receive the same identifier and nothing reports it, because every check the code makes still passes. The configured value is also silently rounded before use, so the start-up line reports a number nobody configured. Validate a seed against Number.MAX_SAFE_INTEGER, not only against integrality, and refuse rather than round. Worth a boundary case wherever a JSON or environment-supplied number becomes an identifier, a counter or a quantity — the same limit turned a 21-digit quantity into 1e+21 on a customer-facing screen in the same run. _(practice, 58daa5a42bfe)_
- **2026-09-23 · v3-qa** — A QA assertion that reads a stored record through a renderer can be blind to the defect the renderer normalises away. A rejection reason typed across three lines was stored with a carriage return the member never typed, breaking a character-for-character criterion; the case compared the stored text against the browser DOM and passed, because HTML parsing drops a CR. Re-read against the bytes on disk and the response bytes, the same case fails. Assert on the record as the system holds it, not as a renderer shows it — and treat any green case that reads through a browser, a JSON parser or a template as unproven until one case in the family has been checked against the raw bytes. _(practice, 5b109c5a5971)_
- **2026-09-23 · v1-architecture** — A mitigation that refuses the empty configuration misses the way the configuration actually goes wrong. An allowlist guard that refuses to start on an absent or empty list still starts cleanly on a list somebody widened to a default route at 6pm to prove the application worked — which is how the restriction is really lost. Make the start-up check refuse the over-broad value too, and have QA start the system once with each bad configuration rather than only with the missing one. _(practice, 67d574e55483)_
- **2026-09-23 · v1-architecture** — A start-up guard that refuses the absent configuration can be exactly the wrong guard when the absent value is the legitimate one. Here an empty part-classification list is a required state — before the owning team has populated it, every claim must be admitted rather than refused — so refusing to start on an empty list, which is the reflex and is what the same codebase correctly does for its network allowlist, would have broken an approved criterion. The dangerous value was the malformed one: a list carrying a class outside the two, or the same part twice, silently changes what the system applies to a customer. Ask of each configuration guard which value is legal-but-empty and which is present-but-wrong, point the refusal at the second, and have QA start the system once with each bad value rather than once with the missing one. _(practice, 699ce7aaede0)_
- **2026-09-23 · d1-brd** — A client asking for a rule to refuse a request at the door, in a system with no customer identity and no way to reach a customer afterwards, is asking for two things that pull apart: fewer refusals reaching the desk, and fewer arguments. The first is delivered by the rule; the second is not, because an unidentified visitor who is refused can resubmit with a better answer, and the desk that by design never sees the refusal cannot tell the second attempt from an honest one. The refusal also stops being evidence — where a human refusal left a thread, an automated one leaves nothing unless a requirement says otherwise. Two requirements follow and neither is in the request: record every door refusal with the values it was computed from, and treat the refusal screen as the only sentence the organisation gets to say, because nothing reaches the visitor after it. Worth applying wherever an eligibility, entitlement or qualification check is being moved from a person to a form. _(practice, 8a0ece3cd96d)_
- **2026-09-23 · v2-build** — A per-criterion check that proves an absence across a whole source directory will be broken by the next increment that legitimately builds the thing it asserts is missing. A check reading "no file reads the visitor's address" was correct while only the customer side existed, and became false the moment the office-network guard was built — not because the criterion changed, but because the check was scoped to the codebase rather than to where the absence is actually claimed. Scope an absence check to the surface the criterion is about, name the files that are allowed to break it so a new one still fails, and record the change as a required change rather than a commit message: a later increment quietly loosening an approved increment's check is invisible in every other artifact. _(practice, 961376e22932)_
