## From the engagement

- **2026-09-26 · d1-brd** — A discount a rep applies from memory is a judgement; the same discount pre-filled by a system is a price policy. When a quote workflow is asked to hold per-reseller discount terms, the requirement is small, but it brings a go-live dependency the request never mentioned: the terms have to be found, written down in one shape, and signed by someone commercial before they are loaded — otherwise the build turns today's habits into policy nobody agreed to. Write the pre-fill, the override-with-reason and the no-terms-on-file path as requirements, and write the signed terms list as a go-live constraint with an owner. Also record the shape you assumed (one number per reseller), because if the terms vary by product, quantity or contract, the requirement grows into a pricing rules table. _(bow-electronics-reseller-portal, note)_
- **2026-09-26 · v2-build** — A per-criterion check is declared as a command before the code exists, and its working directory is part of the command. Written as though it would run from the engagement folder, every check pointed one level up, exited with npm's 'no package.json' code and failed for a reason unrelated to the build; the run recorded 0 of 19 at a commit where every underlying test passed. Run one declared command through the recorder before the first real run, not a hand-run from your own shell, and when the declaration has to be corrected, say so in the declaration so the failed run on the record reads as what it was. _(bow-electronics-reseller-portal, note)_
- **2026-09-26 · v2-build** — Three random line mutations per check across a build that also adds screens, seed data and scripts mostly land where a criterion does not look, so most per-criterion checks 'survive' and the summary reads as weak checks. Given eight mutations the same check noticed a flipped comparison in the route guard. The survival count measures where the mutations fell as much as the checks; the sharper evidence was building the plausible-wrong implementation for three criteria (duplicates refused only at different prices, roles cached at first read, blank part-number rows skipped) — each was caught by exactly the tests owning its criterion and nothing else. Report both, and do not let either stand in for the other. _(bow-electronics-reseller-portal, note)_

## From the practice

- **2026-09-23 · v3-qa** — A rate limiter is the same check-then-act shape as an idempotency token, and the natural way to test one hides the bug completely. A lookup throttle that must refuse the eleventh failure in a window did exactly that sequentially — ten answered, the eleventh refused, at every boundary including the window edge and the lockout lift — and admitted 100 of 100 when the same visitor issued the lookups concurrently. The count was not lost; the lockout armed immediately afterwards. What failed is that every request in the burst read the pre-increment count before any of them wrote. Sequential iteration is how a throttle test gets written, so the whole suite can be green over a control that any caller opening two connections can walk through. Fire the burst concurrently at several widths and compare answered-versus-refused against what the criterion allows; and where a threat was accepted on the record because a control mitigates it, test the control for bypass rather than for presence — the accepted risk is only as accepted as the mitigation is real. _(voltway-returns-portal, note)_
- **2026-09-23 · v3-qa** — A sequence allocator whose configured seed is validated with Number.isInteger accepts values at or above 2^53, where incrementing is a no-op: two records then receive the same identifier and nothing reports it, because every check the code makes still passes. The configured value is also silently rounded before use, so the start-up line reports a number nobody configured. Validate a seed against Number.MAX_SAFE_INTEGER, not only against integrality, and refuse rather than round. Worth a boundary case wherever a JSON or environment-supplied number becomes an identifier, a counter or a quantity — the same limit turned a 21-digit quantity into 1e+21 on a customer-facing screen in the same run. _(voltway-returns-portal, note)_
- **2026-09-23 · v3-qa** — A QA assertion that reads a stored record through a renderer can be blind to the defect the renderer normalises away. A rejection reason typed across three lines was stored with a carriage return the member never typed, breaking a character-for-character criterion; the case compared the stored text against the browser DOM and passed, because HTML parsing drops a CR. Re-read against the bytes on disk and the response bytes, the same case fails. Assert on the record as the system holds it, not as a renderer shows it — and treat any green case that reads through a browser, a JSON parser or a template as unproven until one case in the family has been checked against the raw bytes. _(voltway-returns-portal, note)_
- **2026-09-23 · v3-qa** — Two approved documents can ask for opposite things, and the code can only satisfy one — which makes the failing test a question rather than a defect. Here an approved acceptance criterion required a duplicated row in a configuration list to be survivable (the claim is answered and its class recorded as not established), while the approved architecture's start-up target required the same list to stop the program. The build followed the criterion; a QA case written from the architecture failed; and filing that as a defect would have sent the build team to break an approved criterion to satisfy a document nobody re-read after the backlog changed. Test both documents deliberately where they overlap — configuration guards, start-up refusals and validation rules are where they drift apart — and when they disagree, record the criterion as met, the target as unmet, and the conflict as a question for the operator with a recommendation. The tell is an architecture written before a change request that the backlog absorbed and the architecture did not. _(voltway-warranty-claims, note)_
- **2026-09-23 · v3-qa** — A negative authorization assertion passes for free against a route that does not exist. A case probing that the desk queue refuses an outside caller asserted only 'not 200' and went green — against a path that answers 404 to everyone, including a desk member inside the office. The same wrong path made a later cross-story case fail for an unrelated reason, which is the only way it surfaced; on its own the authorization case would have shipped as evidence that a control works. Pair every must-refuse assertion with a must-succeed one on the same route in the same run: if the entitled caller does not get 200, the refusal proves nothing. The tell is a security case whose evidence contains no successful request. _(voltway-returns-portal, note)_
- **2026-09-23 · v3-qa** — A resident-memory target measured from inside the test runner is not a measurement of the system. A 50,000-entry lookup list was sized by reading process.memoryUsage().rss either side of loading it, in a runner that had already run a hundred other cases; the number it gave (42.9 MB) was wrong in both directions — it carried every earlier case's garbage and none of the real process's baseline. Measured properly, by starting the real process twice from outside and reading its resident set with ps, the same list cost 29-32 MB against a 10 MB ceiling. Memory, file handles and process counts are properties of the deployed process, so measure them on the deployed process, from outside it, twice; a figure taken inside the harness is evidence about the harness. The corollary is that a target the build recorded as never measured is the one worth measuring first: this one had never had a list of that size loaded at all, and it was the only committed target the Epic missed. _(voltway-warranty-claims, note)_
- **2026-09-23 · v3-qa** — A length rule on a browser form has two counts, and only one of them is the user's. A textarea's newlines are normalised to CRLF when the browser serialises the form, so a reason of nineteen characters as typed arrives as twenty and passes a twenty-character minimum — every line break buys one free character against the rule. Boundary cases built from single-line strings cannot see this: the value on the line has to be tested with the content shapes a person actually produces, including a leading newline. Worth a case wherever a minimum or maximum length is enforced server-side on text a browser form submitted. _(voltway-returns-portal, note)_
- **2026-09-23 · v2-build** — An idempotency token that is read before the write and marked after it is check-then-act, and a double-click defeats it: two requests both find the token unspent, both write, and one intent produces two records. The await between the check and the mark is the whole bug, and it is invisible to a test that replays the request sequentially — which is the natural way to write that test. Claim the write before the first await and have the second request wait on it. Worth checking wherever a one-time token, a nonce or a dedupe key guards a write. _(voltway-returns-portal, note)_
- **2026-09-23 · v1-architecture** — A mitigation that refuses the empty configuration misses the way the configuration actually goes wrong. An allowlist guard that refuses to start on an absent or empty list still starts cleanly on a list somebody widened to a default route at 6pm to prove the application worked — which is how the restriction is really lost. Make the start-up check refuse the over-broad value too, and have QA start the system once with each bad configuration rather than only with the missing one. _(voltway-returns-portal, note)_
- **2026-09-23 · v1-architecture** — A start-up guard that refuses the absent configuration can be exactly the wrong guard when the absent value is the legitimate one. Here an empty part-classification list is a required state — before the owning team has populated it, every claim must be admitted rather than refused — so refusing to start on an empty list, which is the reflex and is what the same codebase correctly does for its network allowlist, would have broken an approved criterion. The dangerous value was the malformed one: a list carrying a class outside the two, or the same part twice, silently changes what the system applies to a customer. Ask of each configuration guard which value is legal-but-empty and which is present-but-wrong, point the refusal at the second, and have QA start the system once with each bad value rather than once with the missing one. _(voltway-warranty-claims, note)_
- **2026-09-23 · d1-brd** — A client asking for a rule to refuse a request at the door, in a system with no customer identity and no way to reach a customer afterwards, is asking for two things that pull apart: fewer refusals reaching the desk, and fewer arguments. The first is delivered by the rule; the second is not, because an unidentified visitor who is refused can resubmit with a better answer, and the desk that by design never sees the refusal cannot tell the second attempt from an honest one. The refusal also stops being evidence — where a human refusal left a thread, an automated one leaves nothing unless a requirement says otherwise. Two requirements follow and neither is in the request: record every door refusal with the values it was computed from, and treat the refusal screen as the only sentence the organisation gets to say, because nothing reaches the visitor after it. Worth applying wherever an eligibility, entitlement or qualification check is being moved from a person to a form. _(voltway-warranty-claims, note)_
- **2026-09-23 · v2-build** — A per-criterion check that proves an absence across a whole source directory will be broken by the next increment that legitimately builds the thing it asserts is missing. A check reading "no file reads the visitor's address" was correct while only the customer side existed, and became false the moment the office-network guard was built — not because the criterion changed, but because the check was scoped to the codebase rather than to where the absence is actually claimed. Scope an absence check to the surface the criterion is about, name the files that are allowed to break it so a new one still fails, and record the change as a required change rather than a commit message: a later increment quietly loosening an approved increment's check is invisible in every other artifact. _(voltway-returns-portal, note)_
