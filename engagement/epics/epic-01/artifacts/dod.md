**How every check works.** Each command runs the repository's test entry point (`npm test`, which `raise dod run` executes from the repository root) with `--ac <id>`. The entry point (`scripts/test.mjs`) runs Vitest restricted to the tests whose name carries the tag `[<id>]`. It counts the matching tests itself from Vitest's JSON report, rather than trusting a file count or a total. It exits non-zero if **no** test matched, or if any matching test failed or was skipped. It prints `AC <id> passed` only when at least one tagged test ran and every one passed. A check therefore cannot pass vacuously when a tag is misspelled or a test is deleted. (Practice lesson, voltway-returns-portal 2026-09-23: *the runner's own file-discovery rules are part of the check*. That is why the count is taken from the tagged tests and not from the runner's totals.)

The tagged tests are integration tests unless the row says otherwise. They start the real NestJS server in-process on a fresh SQLite file, with the real migrations and triggers, and drive it over HTTP with a signed-in session cookie and anti-forgery token, the way the browser does. The ERP load tests read a real `.xlsx` generated by the same code that produces `seed/sample-erp.xlsx`.

## What each check must show (written before the code)

The tagged tests for each criterion must assert the following. A test that asserts less does not carry the tag.

- **story-01-01#1**: the sample spreadsheet, whose product-row count N is computed independently of the loader by the generator, is loaded. `loaded + not loaded = N` on the load summary returned by the interface, **and** the store's product count equals `loaded`.
- **story-01-01#2**: for a random sample of 20 rows, and for every row in a small hand-built file, each part number looked up in the store returns the same description and price as the ERP row, with status Open. Prices include sub-cent values such as 0.0040.
- **story-01-01#3**: a row with no part number and a row with no price are each listed as not loaded, with their row number and the reason. So is each bad price shape from T-14: `$12`, `1,234.50`, `#REF!`, a formula, zero and a negative value. None of them is in the store.
- **story-01-01#4**: two rows sharing a part number (with different prices, and also with the same price, per the FDE's decision of 2026-09-26) are **both** listed with reason "duplicate part number". Neither is in the store. Part numbers differing only in case or surrounding spaces count as the same.
- **story-01-01#5**: a load with any not-loaded row reports `complete: false`, and the summary page text does not say the load is complete. A load with no rejected rows reports complete.
- **story-01-02#1**: a price maintainer adds a product. It is then found by its part number, both by exact lookup and through store search. A duplicate part number is refused, and so is an invalid price.
- **story-01-02#2**: a price change from 10.00 to 12.00 adds exactly one history line holding the old price, new price, the user's name and a date and time.
- **story-01-02#3**: three price changes give three history lines, oldest first. An attempt to update or delete a history row directly in the database is refused by the database (append-only trigger).
- **story-01-03#1**: closing an open product makes the product read back with status Closed, and a history row of the product is kept.
- **story-01-04#1**: a rep who is not a price maintainer (rep Sam) is refused a price change (403) and the price is unchanged.
- **story-01-04#2**: rep Sam is refused adding a product and closing one. The product count and the product's status are unchanged.
- **story-01-04#3**: a reseller user is refused every store page (`/sales/store`, the load summary, the product page, add product) and every store interface route.
- **story-01-04#4**: after a reseller user is refused a store page, the refused attempts record (read through the internal admin's refused attempts list) holds that user, the page attempted, and a date and time.
- **story-01-04#5**: rep Sam calling the price-change interface route directly, with a valid session and anti-forgery token (no product page involved), is refused and the price is unchanged. A call without the anti-forgery token is refused too.
- **story-01-05#1**: role manager Morgan names rep Sam a price maintainer. Sam's next price change succeeds.
- **story-01-05#2**: Morgan removes rep Pat from price maintainers. Pat's next price change, from a session that was already signed in, is refused and the price is unchanged (N-09).
- **story-01-05#3**: Morgan names rep Alex a discount setter. Alex can then set a seeded reseller's standard discount, and a discount-change history line is written.
- **story-01-05#4**: Morgan removes rep Lee from discount setters. Lee's next standard-discount change is refused and the discount is unchanged. Being a price maintainer does not grant discounts, and the reverse holds too: the two lists are separate.
- **story-01-05#5**: a rep named for neither (Sam) is refused adding or removing anyone on either list. A price maintainer (Pat) is refused as well. A role manager naming themself is refused (T-08).
